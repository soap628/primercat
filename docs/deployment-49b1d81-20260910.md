## Frontend-only rollback

Do not roll back merely by changing to an old release directory: Compose may
still use the newer `primercat-frontend:latest` image. Explicitly restore the
saved frontend image. Do not run the full-stack deployment script, `compose
down`, a backend rebuild, or a volume/image cleanup as part of this rollback.

First inspect the saved image and verify its ID matches the rollback ID above:

```sh
cd /root/primercat-49b1d81
docker image inspect primercat-frontend:rollback-before-49b1d81 --format '{{.Id}}'
```

Only after confirming that identity, retag the saved image and replace the
frontend alone. Keep `--no-build` so the saved image is not replaced by a build
of the current source:

```sh
docker tag primercat-frontend:rollback-before-49b1d81 primercat-frontend:latest
PRIMERCAT_REFERENCE_ROOT=/opt/primercat/reference-data docker compose -p primercat up -d --no-deps --no-build frontend
```

Confirm the replacement frontend is ready on the internal network before
reloading nginx. Validate the existing nginx configuration:

```sh
docker compose -p primercat exec -T nginx nginx -t
```

If that check succeeds, reload the existing nginx process to refresh the
frontend upstream address:

```sh
docker compose -p primercat exec -T nginx nginx -s reload
```

Verify public pages and their CSS assets again, confirm the running frontend
uses the saved image ID, and compare backend/database/nginx/certbot identities,
startup times and mounts with the pre-rollback snapshot. These steps do not
restart or recreate those other services. Retain both versioned images and the
existing release directories until rollback is no longer needed.
